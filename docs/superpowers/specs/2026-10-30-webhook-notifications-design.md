# Webhook 通知渠道与任务绑定设计

日期：2026-10-30（Asia/Shanghai）

状态：已按用户确认实施，包含业务任务、定时业务任务与定时管理巡检；实现及验证见对应计划。

## 目标与已确认需求

增加独立的、可重复调用的通知能力。首批支持飞书（含 Lark 同协议）、企业微信、钉钉、Slack、Discord、自定义 JSON Webhook。

用户已经确认：

- 平台可独立配置多个渠道。
- 任务创建时选择绑定 0–N 个既有渠道，创建后可以修改。
- 任务运行中的 Agent 根据任务提示词自行判断触发条件、发送时机与消息内容。
- 每次可以选择一个或多个绑定渠道；需要时可以在一次任务中多次发送。
- 绑定是可使用渠道的集合，并不表示每次必须全部发送。
- 消息格式交给 Agent 组织。平台提供渠道格式说明并处理传输、认证与签名。
- 不仅业务插件任务可以通知，定时业务任务和由管理 Agent 执行的定时巡检也必须具备同样的调用能力。

不增加平台业务触发规则、固定完成通知、消息回复入口、聊天机器人会话、短信或邮件接入。现有业务结果回调、HTTP 目标和任务完成协议保持各自职责。

## 路径选择

讨论过复用普通 HTTP 工具、扩展任务结束回调、独立通知渠道三条路径。

普通 HTTP 工具已有 JSON GET/POST，但没有任务渠道绑定、厂商签名与逐渠道发送记录；任务结束回调使用固定平台报文，也限制了执行中的主动调用。用户选择独立的渠道配置和运行时工具。因此增加通知模块，并复用底层配置存储、任务身份、MCP 授权和管理认证，不把通知包装成结束回调。

这是一个涉及 Gateway、管理接口、前端、定时计划和持久化的完整功能；不需要更换 Node.js 24、SQLite、React、TypeScript 或 Ant Design 技术栈。

## 现有实现及边界

- `src/capabilities/catalog.mjs` 的 `http_request` 发送到实时读取的具名 HTTP 目标。
- `src/delivery/configured.mjs` 在任务结束后发送固定结果回调。
- `BusinessRegistry.normalize` 和 `/hooks/...` 当前只接受任务类型、请求标识与业务输入，需显式扩展通知绑定字段。
- `RequestStore.accept` 保存不可变业务插件快照；通知绑定需单独持久化，运行中的发送从最新绑定读取，不修改插件快照。
- 业务 MCP 已校验当前任务身份及工具授权，并为外部操作保存执行记录。通知模块补充更细的批次和逐渠道记录。
- 定时业务计划会创建普通业务任务。管理巡检则进入 Manager 会话，需要把巡检身份和渠道绑定传入该次执行的可信上下文，不能只在业务 MCP 上增加工具。

## 渠道配置

每个渠道具有稳定 ID、可编辑名称、类型、用途说明、启停状态、格式说明、超时、配置版本和私密接入设置。

私密设置包括完整 Webhook URL、认证请求头、Bearer token、签名密钥。Webhook URL 自身通常包含凭证，同样按私密字段处理，不进入 Agent 上下文、工具回包、可分享文档或日志。Admin 配置页显示是否已配置，更新时留空保留，显式清除才清除。所有配置写入采用版本检查，冲突要求重新读取。

渠道类型在创建后固定；要改类型需新建渠道。名称、用途、格式说明、URL、凭证与启停可以修改。类型固定避免旧任务按另一种协议组织报文。

渠道逻辑删除后不再可选或可发送，保留历史记录和原 ID，不能通过重建名称改变旧任务的接收方。停用或删除不自动修改任务状态，也不触发通知。

安全元数据可由管理 Agent 查询；URL、认证与签名等私密字段只由已登录的人在专用 Admin 路由修改，沿用现有插件连接的人机权限分工。业务 Agent 只读取自己绑定渠道的安全元数据。

## 首批协议处理

Agent 提供原生 JSON 消息体，平台不强制统一文本、标题或卡片模板。渠道上下文包含类型、用途、平台维护的常用报文示例和用户补充的格式说明。说明属于参考资料，不能扩大授权。

| 类型 | 平台负责 | 接收成功判断 |
| --- | --- | --- |
| 飞书 / Lark | 原生 JSON POST；可选时间戳和加签 | HTTP 成功且厂商业务码成功 |
| 企业微信 | 原生 JSON POST | HTTP 成功且 `errcode=0` |
| 钉钉 | 原生 JSON POST；可选时间戳及查询参数加签 | HTTP 成功且 `errcode=0` |
| Slack | 原生 JSON POST | HTTP 成功且 Webhook 返回约定成功响应 |
| Discord | 原生 JSON POST；使用确认响应的请求方式 | HTTP 成功且符合执行 Webhook 的响应协议 |
| 自定义 | 原生 JSON POST；可配置私密请求头或 Bearer 认证 | 默认 HTTP 2xx；返回有界、脱敏响应供 Agent 进一步判断 |

实施时须核对官方文档中的签名算法、成功码与响应约定，并用固定时间和已知样例验证签名，不能仅靠同一实现生成的期望值验证自己。飞书和钉钉的签名由平台生成，Agent 不能提供、读取或覆盖签名密钥与平台控制的签名字段。

保持 JSON Webhook 的范围：首批不增加可执行脚本、任意代码转换、上传附件、OAuth 应用机器人或自由选择 HTTP 方法。接收方关键词、IP 白名单、内容限制和访问策略仍由接入方配置。

URL 校验沿用现有 HTTPS／本机 HTTP 规则；固定厂商类型校验对应官方 Webhook 主机与路径，自定义渠道使用显式保存的目标。请求不跟随重定向，不允许 Agent 覆盖目标、认证头或 TLS 设置。Header 校验拒绝换行和传输级保留字段。响应与请求大小均有界。

## 任务创建、绑定与修改

任务创建增加独立的 `notification_channels` 字段（渠道 ID 数组），不塞进业务 `input`，不改变业务结果 schema。省略默认为空。

接入位置：

- `POST /v2/tasks` 和插件 `/hooks/...`。
- 管理 Agent 的 `submit_task`，包括显式试运行。
- 定时业务计划的创建与编辑。

通知仍是显式工具能力：业务插件需要授权通知上下文查询和通知发送工具，才能创建含渠道绑定的任务。无通知能力的插件不能通过新增字段获得该工具。旧插件、旧任务、旧计划默认无绑定，不自动发送。

权限沿用当前“单一操作者或共享管理权限的可信团队”模型：给插件授予通知工具，也代表允许持该插件入口密钥的调用者在创建该插件任务时选择已知渠道 ID。首批不增加按插件的渠道授权池或多租户隔离。公共接口不提供全局渠道枚举、凭证或其他插件的绑定数据；外部调用者由管理员获得所需渠道 ID。

创建时验证数组、去重、渠道存在且未删除、工具已授权；停用渠道允许保留既有绑定，但新选择仅接受可用渠道。无效配置不能静默降级为空。

新增带版本检查的绑定读取和修改操作。Admin 和管理 Agent 可修改任务绑定；外部 API 只能在现有插件密钥／任务所有权范围内修改。运行中的业务 Agent 没有修改自身绑定的工具。

修改规则：

- 新绑定供之后发起的发送使用；不撤回已发消息，不补发历史消息。
- 新发送在真正发起各渠道网络请求前再次检查最新绑定、渠道启停和任务可执行状态。
- 已经发起的网络请求使用该次发起时的配置，无法承诺撤销。
- 插件定义和执行指令快照保持不变；需要时通过实时上下文工具发现新增绑定。
- 已终止任务可以查看记录，不再发送；不开放无意义的终态绑定修改。显式重试创建新任务时默认复制原任务当前绑定，但重新验证渠道及新插件快照的工具授权。重试接口／管理工具增加可选 `notification_channels` 覆盖：省略表示继承，空数组表示清空，非空数组表示本次新任务的选择。Admin 重试前提供预填原绑定的选择控件，失效渠道明确标记并要求移除或替换；不可用时明确报错，不静默丢弃。这样删除渠道不会阻断其他业务的显式重试，也不需要修改终态任务。

## 定时计划

业务 `task` 和管理 `inspection` 两种计划都保存 `notification_channels`，每次触发复制为本次执行的独立绑定。编辑计划影响后续触发；编辑已创建的任务或巡检执行不回写计划，修改计划也不批量修改已创建执行。

保存新选择需验证渠道；停用、删除或配置不可用不阻止计划被关闭。渠道在之后变得不可用时，定时业务任务仍可执行其他工作，继承保存的渠道引用并在通知时返回不可用结果，不因为通知渠道失效阻塞整项业务。由计划触发的受信接入需区分“新选择校验”和“继承历史引用”，而不绕过业务插件／入口就绪检查。

管理 `inspection` 计划在 Gateway 创建巡检记录时同时保存独立绑定。巡检是平台内置的可通知执行类型，不要求为了发送通知而套一层业务插件。触发条件和消息内容同样来自巡检提示词，不强制成功／失败／结束通知。

### 管理巡检的执行身份

为通知记录统一定义执行所有者：业务任务或定时巡检。相同渠道解析、发送适配器、幂等与日志由 Gateway 的通知模块实现，Manager 不自行复制一套外发 HTTP 逻辑。

Manager 接收巡检时，把 Gateway 的巡检 ID 和本地原始执行消息 ID 持久关联。保持现有 claim／去重机制，但必须在 Gateway 确认 conversation/message 对应关系后才允许该消息执行；本地持久化后的消息在映射确认前处于待接入状态，重启恢复也不能越过此步骤，避免当前“先 kick 再 ack”的竞态。

管理 MCP 使用当前 bearer token 对应的可信执行上下文，除 conversation ID 外携带 active message ID 和已核实的巡检来源。通知工具不接受模型传入的任务／会话／巡检身份；通过服务端上下文选择当前巡检，再由 Manager 的内部客户端请求 Gateway。Gateway 校验巡检与原始消息的对应、执行有效性、绑定版本及渠道状态。

只有该次定时巡检原始消息正在执行或恢复时，才允许调用其通知工具。普通管理会话、其他巡检、同一巡检对话里的后续普通消息、已结束执行都不能借用该身份发送。管理操作原本允许配置和建立任务，不应让通知上下文工具间接修改当前绑定。

通知上下文与发送工具的契约在业务 Agent 和巡检 Agent 中保持一致；工具清单按可信上下文暴露，后端仍独立校验，不把“隐藏工具”当作唯一的授权措施。原始巡检任务的通知绑定可由人在计划执行详情中修改，下一次发送读取最新绑定。

Manager 标记执行开始／结束与恢复时，通过内部接口更新 Gateway 的巡检执行状态；请求使用稳定的执行身份协调，不能因 ACK 丢失新建巡检。结束后的失效与重启核对必须覆盖通知仍在发送的窗口：已发请求保留结果，之后的请求被拒绝。网络分区时通知默认拒绝，不根据旧缓存扩大授权。

## Agent 工具

增加一个只读通知上下文工具和一个发送工具。具体名称由实施计划统一，下面为逻辑契约。

上下文工具返回：当前绑定版本、渠道 ID／名称／类型／用途／启停／格式说明／安全示例，以及按游标分页的本任务通知历史。不返回未绑定渠道的配置或私密信息。工具在每次读取时解析最新绑定。

发送工具接受稳定的逻辑通知键和一个发送列表：

```json
{
  "notification_key": "service-check-example-event",
  "deliveries": [
    {
      "channel_id": "00000000-0000-4000-8000-000000000001",
      "body": {
        "msg_type": "text",
        "content": {"text": "发现一项需要检查的问题。"}
      }
    }
  ]
}
```

列表中每项有一个渠道和自己的 JSON 消息体；一个调用可有多项。相同协议的消息体可由 Agent 复用，不同协议各自组织。不得在同一批次中重复同一渠道。平台校验结构、有界大小和各渠道最基本协议字段，细节由厂商返回及 Agent 处理，不引入业务工作流解释器。

发送前先完成整批结构、任务授权与渠道绑定校验。明显越权或格式错误时整批不发送；正常发送阶段某渠道不可用、接收拒绝或网络异常时，分别记录并继续处理其他渠道。必须逐渠道返回结果，聚合状态不能掩盖部分失败。

## 持久化、重复调用与恢复

Gateway 保存独立的执行绑定、通知批次和逐渠道尝试记录。绑定和批次按业务任务或巡检执行归属；每条尝试关联所有者类型／ID、run 或 Manager 原始执行消息、操作 ID、逻辑通知键、渠道 ID、配置版本、时间、HTTP 状态、厂商码和脱敏说明。记录 Agent 提供的消息内容／摘要，不保存带签名的最终请求、私密 URL 或认证头。

同一执行所有者和通知键有唯一约束，并保存整批渠道与原始消息体的摘要。相同键相同内容的重复调用返回已有记录；相同键不同内容报冲突。已确认接收或结果未知的尝试不因重复调用、重启或任务／巡检恢复再次发送。尚未发起的条目可以在重复调用时继续，但须重新校验当前授权与渠道状态。

每个渠道真正发起请求前先持久化尝试状态。进程中断后，已开始但未确认的尝试转为 `unknown`，不自动重放。不同逻辑事件使用不同键；同一事件的重复调用使用同一个键。上下文工具让恢复中的 Agent 能核查旧记录，提示词不得把“未知”描述为失败后随意重试。

状态至少区分 `accepted`、`rejected`、`unavailable`、`unknown` 和尚未发送。`accepted` 只代表接收端确认，不代表群成员已读。平台没有远端恰好一次保证。首批不增加自动重试队列或人工一键重发，Agent 可根据任务要求纠正明确被拒的消息并用新通知键重新发起；未知结果必须先核查。

通知发送结果与业务执行状态、现有结果回调状态分别记录。平台不强制某个通知失败就让业务任务失败，业务提示词决定结果要求。

## Admin 与管理接口

- 系统配置增加独立“通知渠道”分类：列表、新增、编辑、启停、逻辑删除，按类型显示接入字段，提供格式说明及可复制安全示例。
- 新增专用、人类认证且同源校验的渠道写入路由。管理 MCP 无秘密写入／读取／测试发送能力。
- 任务详情增加已绑定渠道编辑与通知历史，使用当前任务绑定版本保存，冲突后明确重新读取。
- 两种定时计划详情均增加渠道选择与独立保存入口，绑定编辑不要求重填 cron 或改变下次触发时间。计划创建继续沿用管理 Agent 工作流；计划的执行历史提供巡检执行绑定和逐渠道通知记录的查看／编辑入口。
- 任务创建继续沿用管理对话和 API，增加参数和文档，不另造完整任务创建页面。
- 可提供明确标记会发送消息的人工“测试通知”动作，只针对已保存渠道，使用后台的固定合成测试文本。保存配置不发送；Agent 不拥有测试入口；测试复用逐渠道记录逻辑并单独归属人工测试历史。
- 中文和英文文案、可访问名称、加载／冲突／失败状态、移动端布局一起完成，保持现有管理台组件与交互约定。

实现时使用专用绑定更新接口，不能让业务发送工具或任意任务输入间接更新绑定。Manager 调用 Gateway 的渠道配置与测试方法不得出现在公开 Agent 工具清单中。

## 升级、清理与文档

采用可重复执行的 SQLite 迁移。旧安装升级后无渠道、无绑定、无通知副作用。历史任务业务定义可继续编译。现有 HTTP 目标和回调不自动迁移成通知渠道。

任务历史清理同步删除归属该任务的绑定、批次和尝试；正在发送的执行受保护，避免清理与外发竞态。Gateway 的巡检历史清理也需检查运行中的巡检及通知，并删除其归属记录。Manager 删除巡检对话时，在本地事务中保存持久的 Gateway 通知历史清理任务，跨服务清理失败可重试，不让孤立通知历史无限保留。已删除渠道的历史元数据可保留，不能阻止详情和过期清理。人工测试记录采用有界分页和既有保留策略清理，不无限增长。

更新中英文 README、架构、插件／API 对接文档、平台管理规则和工具清单。对接文档需要描述创建绑定、读取、修改、冲突、通知记录，以及定时计划与任务绑定的区别。部署打包、Manager 可读源码清单和发布检查纳入新模块。首批不更改版本号、创建发布或进行生产部署。

## 验收与验证

全部使用合成数据、固定时间和本地 HTTP 接收端，不读取真实账号或向真实渠道发送消息。

1. 六类渠道的 JSON 发送；飞书／钉钉独立签名样例；各厂商 HTTP 成功但业务失败；Slack／Discord 成功响应；自定义头与响应脱敏。
2. 多渠道部分失败、超时、断开、限流、重定向、响应过大、配置变化和渠道停用／删除。
3. 创建 0／1／多个绑定、未绑定越权、无通知能力插件、插件 API 范围、绑定版本冲突，以及运行中修改对后续调用生效。
4. 两种定时计划触发复制与之后独立修改、停用失效渠道不阻塞关闭计划、不可用通知不吞掉业务任务、重试继承及显式覆盖／清空；管理巡检确实可以发送。
5. 重复通知键、内容冲突、恢复未知尝试不重放、并发相同键只发一次、未发送条目继续前重新授权。
6. 凭证与完整 Webhook URL 不进入 Agent 元数据、错误、通知历史、共享文档或日志；人类写入接口保持认证与同源校验。
7. 数据迁移、历史清理与发送竞态、原有任务结果／回调／HTTP 目标回归。
8. Admin 渠道配置、绑定编辑、逐渠道历史、冲突反馈、可访问性和移动端浏览器测试。
9. Node.js 24 下运行 `npm test`、`npm run check:release`、相关 Playwright 测试，并核对新源码及生成前端的打包与 Docker 目标。
10. 巡检接入确认后才执行；可信消息身份绑定；普通管理会话／后续消息／其他巡检不能冒用；恢复不重复发送；Manager 与 Gateway 失联时拒绝外发；巡检对话清理可恢复。

## 由实施者决定的细节

在上述行为不变的前提下，实施计划决定文件拆分、精确表名与路由名称、工具名称、大小上限、有界并发、分页默认值和页面控件排列。首选原生 `fetch` 和 `node:crypto`，避免为少量 HTTP 协议引入 SDK 或执行第三方脚本。

## 本设计中需用户留意的默认选择

- 外部插件调用者的通知选择权限来自插件显式授予的通知工具；不另设插件渠道授权池。
- 首批覆盖普通业务任务、定时业务任务和定时管理巡检；巡检通知权限只属于该次巡检的原始执行消息。
- 已结束任务不修改绑定；显式重试复制绑定并重新校验。
- 自定义 Webhook 默认以 HTTP 2xx 判定接收，业务响应留给 Agent 判断。
- 接收结果未知不自动重试；不承诺远端恰好一次。

## 设计审阅记录

实施前审阅指出：终态任务不允许修改绑定时，重试必须另有修改渠道的入口。已明确重试覆盖参数和 Admin 重试选择控件，避免失效渠道阻断重试。

另评估了让所有插件无需通知能力授权即可外发的候选方案。此方案会让任意插件入口密钥都能选择已知渠道并获得外发权限，因此本设计不采用：保留业务插件显式通知工具授权，管理员可通过现有管理 Agent 创建／更新该能力；定时巡检由平台按巡检身份和显式渠道绑定授权。独立渠道配置不等于扩大现有入口密钥权限。

修订后再次审阅，未发现进入实施计划前仍必须回答的重要遗漏。
