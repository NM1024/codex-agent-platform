# Codex Agent Platform 系统运维页面与处理方案

Approved Pages design: https://chatgpt.com/space/page_5f726d6e7d2481918a15bebfa32f9a2b

增加统一的系统运维入口，让用户和管理 Agent 可以查询平台内部工作、定位持续异常、执行受控处理并核验恢复。页面先在 Pages 预览，实际控制台继续使用既有 React、Ant Design 主题与组件。业务任务结果保持原有记录，系统运维只关联必要的任务或操作编号，不复制业务正文。

# 页面与交互

主导航新增“系统运维”，放在“系统配置”之前。页面包含“待处理问题”“后台工作”“系统日志”三个页签，顶部显示需要处理、等待重试、正在运行和最近恢复的汇总，显示最近采集时间与部分服务不可达状态。沿用绿色主色 #345e4f、冷灰背景 #f3f6f8、白色卡片、现有语义状态色、36px 控件、12px 卡片圆角及统一详情抽屉。桌面使用表格，手机切换带字段标签的记录卡片；不通过缩小字号容纳宽表。

待处理问题默认只显示未恢复的问题，可按服务、模块、状态、时间筛选，并按关键词、错误码或关联编号搜索。详情展示首次出现、最近出现、累计次数、最近进展、影响范围、当前证据、下次重试和处理经过。动作包括查看关联日志、交给管理 Agent 分析、执行适用的受控处理、查看或生成 GitHub issue 草稿。没有可执行动作时给出原因。

后台工作显示清理、同步、事件回传、巡检交接、恢复核对等工作的真实进度。区分等待、执行中、等待重试、需要人工处理、结果待确认、已完成、未启用或不适用。系统日志提供时间范围、级别、服务、模块与结果筛选、关键词搜索、游标分页和详情。保留已有数据时刷新失败须显示数据可能过期，不能用空表代表没有问题。

# 核心链路覆盖

| 链路 | 必须补齐的证据和处理能力 |
| --- | --- |
| 管理对话目录与附件清理 | 授权删除后的待清理对象、失败码、重试次数、完成时间、定向重试 |
| Runner 临时目录回收 | 运行结束后的清理失败、遗留对象、限定归属的重试 |
| 沙箱与闲置容器 | 当前能力状态、销毁和回收结果、当前对话与全局待清理状态；宿主不可达不冒充已完成 |
| 历史保留扫描与空间回收 | 扫描进度、跳过原因、失败数量、数据库回收结果 |
| 配置应用与 Runner 同步 | 保存版本、期望版本、最后确认版本、同步结果、重新同步 |
| Runner 事件回传 | 待发送数量、最老等待时间、最近失败、幂等重新投递 |
| 调度与巡检交接 | 触发、claim、ACK、状态回写和通知清理的阶段与阻塞原因 |
| 重启恢复与运行核对 | 恢复起止、采用原运行、失败或待确认原因、重新核对 |
| 通知与最终回调传输 | 关联既有发送记录；failed 与 unknown 分开，不自动重发未知外部效果 |
| 服务健康与模型连接 | 启停、失联、探测结果变化、登录与模型不可用；普通空闲和未启用不报警 |
| 接口与管理操作 | 请求或操作编号、脱敏错误、谁执行了哪种处理、确认和复核结果 |
| 升级与宿主服务 | 接入允许公开的阶段、结果和诊断摘要；保留宿主权限边界 |
| 日志采集自身 | 写入失败、数据截断、来源缺失和容量限制必须可感知 |

# 数据与部署边界

各服务维护自己拥有的结构化系统事件和后台状态，通过固定内部接口汇总；不让 Manager 直接查询其他服务数据库，也不引入 Docker socket、任意日志文件读取或主机 Shell。记录独立于管理对话及业务历史，删除对话不能删除系统处理经过。使用现有 Node.js 24、SQLite 和内部认证机制，不新增外部日志平台作为运行依赖。

事件记录包含时间、事件编号、服务、模块、级别、错误码、关联操作编号、目标类型与脱敏摘要。后台工作状态另外记录阶段、首次与最近尝试、最近成功与进展、尝试次数、待处理数、下次重试和当前阻塞原因。问题按稳定指纹合并，保存出现和恢复事件；日志级别不等于问题是否仍然存在，关闭问题必须有新检查证据。

所有查询有数量、时间范围和输出长度限制，支持分页。系统日志、已完成后台工作和已恢复问题的历史记录统一遵循现有 retention 配置的 enabled 开关与 days 保留天数，不另设 30 天规则；清理流程继续采用每天分批扫描和每分钟推进。未完成工作、未恢复问题及其必要证据受保护，删除管理对话不会删除这些系统记录。日志存储故障不能推翻已经成功提交的业务结果；必须提供标准错误输出和可见的采集异常作为回退。跨服务查询失联时返回部分结果、来源状态与采集时间。

# 重试与状态规则

常规探测、清理、同步和重试仍由确定性的后台程序执行，不逐次启动模型。短暂网络错误采用退避和去重；重复失败聚合计数，达到模块规定的关注条件后显示需要处理。权限、无效配置等问题避免每分钟无效重试。保留原待处理工作，不能为了消除报警而删除队列。

未启用的可选能力不等于故障。只有能够确认没有远端资源需要回收时才将清理标记为不适用；历史状态不明确或远端不可达时仍保留待确认记录。通知、回调、代码执行和 GitHub 上报等外部写入结果未知时，先读取现状或去重核实，不使用新请求编号盲目重放。

# 管理 Agent 能力与权限

管理 Agent 获得与页面相同的系统日志查询、系统状态和问题详情查询工具，并获得有明确参数与归属校验的维护工具：重新同步、重新核对、重试已授权的清理与内部事件交接。每次动作记录操作者、目标、前置状态、结果和复核证据。修改配置必须沿用版本冲突检查；不能通过日志文字授权额外动作。

现有暂停领取、并发调整、配置更新和 Gateway 或 Runner 重启工具继续适用。会中断工作、删除新的数据、改变凭证或影响外部副作用的动作按原权限与人工确认处理。修复工具使用固定动作清单，拒绝任意命令、SQL、路径和未知目标。管理 Agent 不修改平台源码、不部署、不回滚数据库，也不自动重试已经结束的业务任务。

模型或账号故障可能使管理 Agent 自身不可用，因此常规查看、简单搜索和必要的受控操作必须可以直接在页面完成。服务彻底停机时仍保留运维人员可用的部署和宿主日志入口，不能承诺所有故障都由平台自救。

# 代码问题反馈到 GitHub

若证据表明问题来自平台代码，管理 Agent 停止应用不适合的运维修复，整理为候选代码缺陷：平台版本、影响、预期与实际结果、复现步骤、发生时间、脱敏错误码、操作编号、相关源码位置和已尝试的处理。无法证明根因时明确标注推测。开发者部署修复或人工重新诊断后，管理员可按当前版本将问题重新开放维护；这只解除代码缺陷分类限制，不代表已经恢复，也不会执行修复。此入口仅供人工使用，管理 Agent 无法调用。

若部署平台已经配置专用的受限 GitHub 上报能力，可向管理员允许的项目仓库提交 issue；提交前按问题指纹核对已有报告，保存 issue URL 与问题关联。请求结果未知时先查找已有报告，不再次盲目创建。平台内 Agent 不会自动继承本次 ChatGPT 对话的 GitHub 连接。未具备直接提交条件时，以当前对话的脱敏草稿作为完整交付，不为上报引入任意主机或代码写入权限。

没有可用的直接提交授权时，管理 Agent 在当前对话中给出完整的脱敏 issue 草稿，包含版本、影响、复现步骤、预期与实际结果、证据和已尝试的处理，由用户自行发布或处理。草稿可复制，未实际提交时明确标注未提交。生成草稿不依赖 GitHub 连接，也不要求用户在聊天中提供 token。敏感日志、用户业务正文、凭证和真实部署地址不得进入公开反馈。

# 实现方式选择

| 方式 | 取舍 |
| --- | --- |
| 仅汇总容器与宿主文本日志 | 改动较小，但不能补回忽略的错误，也不能准确描述后台工作是否完成 |
| 统一结构化事件与后台状态并提供受控工具 | 已选方向。覆盖界面查询、问题追踪、Agent 分析和复核，保持现有服务数据归属 |
| 引入完整外部日志平台 | 当前部署规模下成本和维护负担较高，保留未来导出接口，不作为第一版依赖 |

# 验收要求

先通过 Pages 交互预览核对页面，再实现实际控制台。验证中英文、桌面、320px 手机、空数据、来源部分失联、翻页与筛选、刷新失败保留旧数据。后端用合成数据和本地接收端验证事件脱敏、稳定分页、工作状态、恢复证据、幂等重试、重启持久性、跨服务认证、修复权限、GitHub 去重与未知结果处理。不得使用真实账号提交模型任务或真实 issue 进行测试。最终运行 npm test、npm run check:release 和相关浏览器回归。
