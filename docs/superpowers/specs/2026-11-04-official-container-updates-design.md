# Official container and source updates

The operator requested both source-build updates and official prebuilt-container updates. Official images should reduce build work and cache growth on the deployment host. Both methods use the existing installation, private data directories, backup, consistent database validation, healthy-container verification and manual recovery contract. Release and merge authorization already exists in the conversation; Pages must precede UI implementation.

## Decisions

- New updater default: `image`; explicit alternate: `source`. Normal `deploy.sh build` remains a source build. `deploy.sh pull` prepares official images. CLI and version dialog expose the same two choices. There is no user-supplied registry, shell, path or image reference in the web upgrade API.
- Publish four Linux amd64 images for the platform's currently documented supported architecture: gateway, runner, manager and sandbox. Other architectures use source build until independently supported and tested. Do not silently fall back to a server-side source build.
- Use GHCR under `ghcr.io/nm1024/codex-agent-platform-{component}`. Also publish a checksum-verified combined Docker image archive in GitHub Releases, preserving shared layers, so official-container updates work through the same already-supported GitHub download route when GHCR anonymous access is unavailable. Both transports carry the same image IDs and exact tested source revision. Initial GHCR package public visibility may require owner settings because the available API has no visibility mutation; the public Release archive must provide a fully working official-image path independently.
- Keep Compose image names `codex-agent-platform-{component}:VERSION`. Official pull/load verifies fixed publisher, version, architecture, source revision and immutable image IDs before assigning these local aliases. Existing discovery, mounts and old updater image-verification behavior remain compatible. Source and official methods may share layers but never mix service versions.
- New `container-images.json` release asset: schema_version=1, version, revision (40 hex), platform=`linux/amd64`, archive={name,size,sha256}, and images keyed by the four fixed components, each with local_tag, id (`sha256:`), registry (fixed official repo plus optional immutable digest). The manifest and image archive are covered by `SHA256SUMS`. Reject missing/extra components, arbitrary repos, invalid digests, wrong version/platform/revision and oversized downloads before stopping services. A successful Docker import alone does not establish deployment success.
- Image acquisition and validation occur before service stop. Persistent deployment metadata records the method. An explicit method change at the same version may redeploy through the same backup and validation sequence; unchanged version/method remains a verified no-op. Preserve the legacy no-op contract for older deployment state lacking a method.
- Existing installed updater compatibility: new staged `deploy.sh build`, when `PLATFORM_UPDATE_STAGED=1`, prepares official images by default unless the fixed environment selector says `source`. Existing v1.0.7 web workers can therefore use the new release without first replacing themselves. All ordinary build invocations still compile source. Legacy web helpers that advertise no method capability accept only the legacy empty request. Their UI says this upgrade uses the release default, disables method selection, and sends no method, rather than falsely calling it source-only. For the new staged release that default is official images.
- Use a small Python module for image release validation/acquisition, shared by deploy.sh and update-release.py. The downloaded update bootstrap remains standalone standard-library Python; image helpers are loaded from the staged release only after verified extraction. The installed host helper refresh list includes this dependency; all subprocess entrypoints retain fixed argument vectors and existing trust checks. Preserve ProtectSystem=full and optional sandbox setup behavior.
- Optimise Docker dependency layers: normalize only root application versions in install manifests in an earlier stage; reuse stable dependency manifests across application-only releases; restore original package files after installation. Keep actual dependency versions/integrities unchanged. Remove npm download cache within install layers. Keep production images free of development dependencies and platform credentials.
- Old images: expose a scoped cleanup command, default dry run, retaining the newest three project versions and any image referenced by any running or stopped container. Mutating cleanup requires an explicit command flag. Do not run a global Docker prune, delete data/volumes, or remove other repositories' tags. Automatic deletion is not required for shipping the two update methods; reduced build churn is the immediate disk saving.

## Version dialog

Use the existing version modal, colours, type, spacing and primary action. Add a compact labelled choice above the upgrade action: `官方镜像（推荐）` and `源码构建`. Show one short explanation based on choice. Confirmation says prepare images/source, back up and restart. CLI copy command includes the selected method and supports the existing runtime-directory argument. Busy jobs lock method selection and display their actual method when available. Old helpers show a release-default explanation with disabled method selection instead of sending unsupported fields. Reopening a successful installed job stays quiet as before.

## Publishing and verification

Build and test the release targets once, publish official images only from a successful exact-commit CI proof, label all images with version/revision/source/component, and upload the image manifest/archive alongside existing source/update assets. Verify published public assets and anonymous image/archive acquisition before promoting the stable release. Never publish a broken image-capable release. Source-only historical releases remain readable, with a clear unsupported-image error on explicit image selection.

Tests use synthetic data. Cover closed method requests, durable duplicate-job admission, old helper compatibility, download and manifest tampering, no stop on acquisition failure, same-version method changes, mixed-image rejection, private data preservation, source and official image update success/no-op, and both methods' manual recovery evidence. Docker-layer checks must establish unchanged dependency manifests across app-version-only changes. Browser checks cover method choice, copied command, confirmation, legacy default-method helper, busy lock, reconnect, and Chinese/English narrow layouts. Run repository-required npm/release checks and actual Compose update scenarios for both methods before release.

## Alternatives

Keeping source-only updates leaves server build/cache pressure unchanged. Registry-only delivery depends on GHCR visibility and server connectivity. The selected design keeps source build and supports both official registry and versioned image archives, trading one extra release asset for a reliable official-container path.
